# automationdiscrepancyones

Сервис сверки документов и количественных остатков между базой 1С «Управление торговлей» и бухгалтерскими базами БУХ2019/БУХ2026. Приложение получает выгрузки по HTTP, нормализует строки, находит расхождения и формирует список действий в Excel `.xlsx`.

## Функциональность

- Web-форма для запуска сверки за произвольный период.
- Загрузка списка складов из 1С через endpoint `/warehouses`.
- Фильтрация сверки по выбранным складам.
- Получение данных из базы управления торговлей и налоговых баз через HTTP GET.
- Поддержка базовой HTTP-авторизации для подключений к 1С.
- Нормализация русских и англоязычных имен полей выгрузки.
- Нормализация сумм с пробелами, неразрывными пробелами и запятой в качестве десятичного разделителя.
- Поиск отсутствующих, лишних и дублирующих документов.
- Сравнение количественных остатков на начало и конец выбранного периода.
- Проверка по подтверждённому списку типов документов товарного движения.
- Формирование Excel-отчета с типом расхождения и рекомендацией.
- Unit-тесты для нормализации, валидации запроса, клиента 1С, сверки и генерации отчета.

## Установка в Linux

Для Ubuntu/Debian установите Python и модуль виртуальных окружений:

```bash
sudo apt-get update
sudo apt-get install -y python3 python3-venv
cd /opt/integration-ones
python3 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env
chmod 600 .env
```

Заполните `.env`, затем проверьте ручной запуск:

```bash
./run.sh
```

Скрипт принимает переменные `PYTHON_BIN`, `HOST`, `PORT` и `WORKERS`. По умолчанию
используются `.venv/bin/python`, `service.example.invalid`, `8000` и один worker.

Для постоянной работы создайте системного пользователя и установите unit-файл:

```bash
sudo useradd --system --home /opt/integration-ones --shell /usr/sbin/nologin integration-ones
sudo chown -R integration-ones:integration-ones /opt/integration-ones
sudo cp deploy/integration-ones.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now integration-ones.service
sudo systemctl status integration-ones.service
```

Unit-файл не подключает `.env` через директиву `EnvironmentFile`: приложение читает файл
самостоятельно, не изменяя кавычки внутри JSON-параметров конфигурации.

Проверка сервиса и журнала:

```bash
curl http://127.0.0.1:8000/health
sudo journalctl -u integration-ones.service -n 100 --no-pager
```

Чтобы открыть сервис только для локальной подсети через UFW, правило создаёт администратор,
например: `sudo ufw allow from service.example.invalid/24 to any port 8000 proto tcp`.

## Настройка

Создайте локальный файл настроек из примера. В Linux используется `cp .env.example .env`,
в Windows:

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

Заполните реальные параметры подключений:

```env
ONEC_TRADE_NAME=Управление торговлей
ONEC_TRADE_BASE_ID=trade
ONEC_TRADE_URL=https://internal.internal.example.invalid/trade/remainders
ONEC_TRADE_WAREHOUSES_URL=https://internal.internal.example.invalid/trade/warehouses
ONEC_TRADE_USERNAME=readonly_user
ONEC_TRADE_PASSWORD=readonly_REDACTED
ONEC_TRADE_REQUEST_METHOD=GET
ONEC_TRADE_REQUEST_PAYLOAD=json
ONEC_TRADE_SUPPORTS_WAREHOUSE_FILTER=true
ONEC_TRADE_DATE_FORMAT=%Y%m%d
ONEC_TRADE_PERIOD_BEGIN_KEY=periodBegin
ONEC_TRADE_PERIOD_END_KEY=periodEnd
ONEC_TAX_BASES_JSON=[{"base_id":"buh2019","name":"БУХ2019","url":"https://internal.internal.example.invalid/buh2019/remainders","warehouses_url":"https://internal.internal.example.invalid/buh2019/warehouses","username_env":"ONEC_TRADE_USERNAME","REDACTED_env":"ONEC_TRADE_PASSWORD","request_method":"GET","request_payload":"json","date_format":"%Y%m%d","period_begin_key":"periodBegin","period_end_key":"periodEnd","supports_warehouse_filter":true}]
ONEC_WAREHOUSE_MAPPINGS_JSON=[]
ONEC_HTTP_TIMEOUT_SECONDS=120
ONEC_AMOUNT_TOLERANCE=0.01
ONEC_QUANTITY_TOLERANCE=0
ONEC_RETRY_MAX_ATTEMPTS=3
ONEC_RETRY_BACKOFF_SECONDS=0.2
ONEC_MAX_CONCURRENT_RECONCILIATIONS=2
```

Параметры:

- `ONEC_TRADE_NAME` - отображаемое имя базы управления торговлей.
- `ONEC_TRADE_URL` - endpoint выгрузки строк из базы управления торговлей.
- `ONEC_TRADE_WAREHOUSES_URL` - endpoint получения списка складов.
- `ONEC_TRADE_USERNAME` и `ONEC_TRADE_PASSWORD` - учетные данные для базы управления торговлей.
- `ONEC_TAX_BASES_JSON` - JSON-массив бухгалтерских баз со стабильным `base_id`, URL выгрузки и справочника складов.
- `ONEC_WAREHOUSE_MAPPINGS_JSON` - необязательные ручные исключения. Основные соответствия строятся автоматически по `СкладБухгалтерия` из УТ и названию `Склад` в каждой БУХ. Значением кода может быть строка или список.
- `ONEC_HTTP_TIMEOUT_SECONDS` - timeout HTTP-запросов к 1С.
- `ONEC_AMOUNT_TOLERANCE` сохранён для совместимости настроек; суммы не участвуют в пользовательской сверке.
- `ONEC_QUANTITY_TOLERANCE` задаёт допустимое расхождение количества.
- `ONEC_RETRY_MAX_ATTEMPTS` - число попыток одного запроса к 1С. Повторяются таймауты,
  обрывы соединения (включая обрыв внутри тела ответа) и статусы 408, 429, 500, 502, 503, 504.
  Остальные 4xx и ошибки конфигурации не повторяются.
- `ONEC_RETRY_BACKOFF_SECONDS` - базовая задержка между попытками. Она удваивается с каждой
  попыткой и ограничена пятью секундами.
- `ONEC_MAX_CONCURRENT_RECONCILIATIONS` - сколько сверок выполняется одновременно. Запросы
  сверх лимита сразу получают HTTP 503 с заголовком `Retry-After`, а не встают в очередь.

Худшее время одного обращения к 1С равно `ONEC_RETRY_MAX_ATTEMPTS` × `ONEC_HTTP_TIMEOUT_SECONDS`
плюс сумма задержек: при значениях по умолчанию около 361 секунды.

Для `POST /reconcile` это время складывается по базам. Если управление торговлей исчерпает
все попытки, запрос завершится ошибкой примерно через 361 секунду. Если управление торговлей
ответит, а обе бухгалтерские базы окажутся недоступны, ожидание вырастет примерно до
2 × 361 секунды, после чего отчёт вернётся с непроверенными базами. Таймаут обратного прокси
(`proxy_read_timeout` в nginx) должен быть не меньше этой величины, иначе оператор получит
ошибку шлюза раньше, чем сервис закончит повторы. Уменьшить ожидание можно только снижением
`ONEC_HTTP_TIMEOUT_SECONDS` или `ONEC_RETRY_MAX_ATTEMPTS`.

Повтор применяется и к базам, настроенным на `request_method=POST`. Сервис использует POST
только как способ передать период выборки, поэтому повтор безопасен. Если в `ONEC_TAX_BASES_JSON`
появится endpoint, который на POST изменяет данные в 1С, повторы для него нужно отключить
значением `ONEC_RETRY_MAX_ATTEMPTS=1`.

Одна сверка держит в памяти выгрузки всех трёх баз, поэтому предел параллелизма напрямую
определяет пиковое потребление памяти. Systemd-unit ограничивает процесс директивами
`MemoryHigh` и `MemoryMax`.

## Формат обмена с 1С

Для выгрузки строк сервис отправляет GET-запрос с JSON-телом:

```text
GET <url>
{"periodBegin":"YYYYMMDD","periodEnd":"YYYYMMDD"}
```

1С принимает один код склада за запрос. Для единственного физического кода приложение использует серверный фильтр; для группы из нескольких кодов оно один раз получает полную выгрузку базы и фильтрует её локально:

```text
GET <url>
{"periodBegin":"YYYYMMDD","periodEnd":"YYYYMMDD","warehouse":"КОД-БАЗЫ"}
```

Endpoint складов вызывается без параметров:

```text
GET <ONEC_TRADE_WAREHOUSES_URL>
```

Фактический ответ справочника 1С:

```json
{"code":200,"data":[{"Склад":"Секция 1","Код":"TRADE-001","Группа":"Основные","СкладБухгалтерия":"Основной склад"}]}
```

Точные повторы одного склада схлопываются. Конфликтующие записи с одинаковым кодом отклоняются.

Выгрузка строк должна быть списком объектов или объектом с ключом `data`, `items`, `rows` или `result`.

Поддерживаемые поля строки:

| Каноническое поле | Алиасы |
| --- | --- |
| `period` | `period`, `Период`, `период` |
| `document` | `document`, `Документ`, `документ` |
| `nomenclature_code` | `nomenclature_code`, `НоменклатураКод` |
| `article` | `article`, `НоменклатураАртикул` |
| `warehouse_code` | `warehouse_code`, `СкладКод` |
| Остатки и обороты | `КоличествоНачальныйОстаток`, `КоличествоОборот`, `КоличествоКонечныйОстаток` и соответствующие поля стоимости/суммы |
| `sender_warehouse` | `sender_warehouse`, `СкладОтправитель` |
| `receiver_warehouse` | `receiver_warehouse`, `СкладПолучатель` |
| `document_id` | `document_id`, `ДокументGUID`, `ДокументUUID`, `ДокументУИД` |
| `source_document_id` | `source_document_id`, `ИсходныйДокументGUID`, `ДокументОснованиеGUID`, `ДокументОснованиеУИД` |

Если `period` отсутствует, сервис подставляет период запроса в формате `DD.MM.YYYY-DD.MM.YYYY`.

## API

### `GET /`

Возвращает HTML-форму запуска сверки.

### `GET /health`

Возвращает статус приложения:

```json
{"status":"ok"}
```

### `GET /warehouses`

Загружает справочники складов УТ и всех бухгалтерских баз. Склады УТ группируются по `СкладБухгалтерия`, после чего значение связывается с полем `Склад` каждой БУХ. В выбор попадают только связи, разрешённые во всех базах.

Пример ответа:

```json
{
  "bases": [
    {"id": "trade", "name": "Управление торговлей", "warehouses": [{"code": "TRADE-001", "name": "Секция 1", "group": "", "accounting_name": "Основной склад"}]}
  ],
  "warehouses": [
    {"id": "auto:buh2019:BUH-001", "label": "Основной склад", "sources": {"trade": [{"code": "TRADE-001", "name": "Секция 1", "group": ""}], "buh2019": [{"code": "BUH-001", "name": "Основной склад", "group": ""}]}}
  ],
  "mapping_diagnostics": {
    "mapped_logical_count": 1,
    "mapped_trade_count": 1,
    "blank_trade_count": 0,
    "unresolved_trade_count": 0,
    "unresolved_links": [],
    "unreferenced_accounting": []
  }
}
```

### `POST /reconcile`

Запускает сверку и возвращает Excel-файл с заголовком `Content-Disposition: attachment`.
Бухгалтерские базы обрабатываются независимо. Заголовок `X-Unchecked-Base-Count`
содержит количество баз, которые не удалось проверить.

Если уже выполняется `ONEC_MAX_CONCURRENT_RECONCILIATIONS` сверок, запрос сразу получает
HTTP 503 с заголовком `Retry-After`. Это защищает 1С от одновременных полных выгрузок под
одной сервисной учётной записью.

Тело запроса:

```json
{
  "start_date": "2024-01-01",
  "end_date": "2024-01-31",
  "warehouses": ["main"]
}
```

`warehouses` содержит логические ID из `GET /warehouses`. Поле можно не передавать или передать пустым массивом, тогда сверка выполняется без фильтра по складам. Перед фильтрованной сверкой справочники загружаются повторно; неизвестный или устаревший ID отклоняется с HTTP 422 до обращения к выгрузкам остатков и движений.

Пример ручного запроса:

```powershell
Invoke-WebRequest `
  -Uri "http://127.0.0.1:8000/reconcile" `
  -Method POST `
  -ContentType "application/json" `
  -Body '{"start_date":"2024-01-01","end_date":"2024-01-31","warehouses":["main"]}' `
  -OutFile ".\Список_документов_для_исправления_2024-01-01_2024-01-31.xlsx"
```

## Отчет

Стандартный отчёт объединяет расхождения остатков и список действий на уровне документов.
Несколько товарных строк одного документа объединяются по типу, номеру, точной
дате/времени и складу.

- `Итоги` показывает количество документов, требующих исправления и ручной проверки.
- `Расхождения остатков` показывает только несовпавшие начальные и конечные остатки
  по каждому товару отдельно для БУХ2019 и БУХ2026.
- `Довнести в БУХ` содержит документы УТ, отсутствующие в соответствующей бухгалтерской базе.
- `Лишние в БУХ` содержит лишние документы и дубли бухгалтерской базы.
- `Проверить вручную` содержит неоднозначные совпадения и документы, которые могут законно
  существовать только в бухгалтерии.
- `Базы не проверены` содержит ошибки недоступных или непригодных выгрузок. Документы таких
  баз не попадают в списки исправлений и не блокируют результаты остальных баз.

На листе `Итоги` также указаны количество документов УТ и БУХ, число сопоставленных,
недостающих, лишних и неоднозначных документов, исключённые типы, документы с ожидающим
правилом и количество расхождений остатков отдельно для каждой проверенной базы.

В каждой строке указаны конкретное действие, база, тип, номер и дата документа, исходные
представления УТ/БУХ и склады. Документы и остатки сравниваются по количеству. Расхождение
только в стоимости не считается ошибкой и не попадает в пользовательский отчёт.

Одна строка листа `Расхождения остатков` соответствует конкретной бухгалтерской базе,
логическому складу, номенклатуре и контрольной дате. Первые колонки показывают дату,
артикул, наименование, остаток в УТ, остаток в конкретной БУХ и разницу `БУХ − УТ`.
Далее указаны база, тип остатка, причина, код и склады. Начальный остаток относится к
`start_date`, конечный — к `end_date`.
Если строка есть только с одной стороны, для отсутствующей стороны выводится ноль и причина
`Нет остатка в УТ` или `Нет остатка в БУХ`. Сервис формирует отчёт, но не изменяет документы
и остатки в 1С.

Полное каноническое описание требований находится в
[`docs/technical-specification.md`](docs/technical-specification.md).

## Правила сопоставления

GUID для сопоставления не требуется. Документы сопоставляются последовательно:

1. По совместимой группе типа, номеру и точным дате/времени. Передача филиалу и перемещение считаются одной группой.
2. Реализации с разными номерами сопоставляются только при уникальном совпадении даты/времени, состава товаров и количества движения.
3. Пустые документы с граничными остатками сопоставляются по дате, товару и логическому складу.

Неоднозначное совпадение не выбирается автоматически. Внутренние перемещения между
физическими складами одного логического склада исключаются из списка пропущенных.
Повторные строки одной номенклатуры внутри документа суммируются перед сравнением.
Для сопоставленного документа проверяются только обороты; начальный и конечный остатки
проверяются отдельно по контрольным строкам без документа.

В автоматическую сверку входят перемещения и передачи филиалу, поступления товаров и
услуг, реализации, оприходования и списания. `Поступление дополнительных расходов`,
`Заказ покупателя` и неизвестные типы исключаются. `Комплектация номенклатуры`,
`Требование-накладная` и `Безвозмездная передача` ожидают согласованного признака вида
документа от 1С и до этого не создают автоматических рекомендаций. Флаги отражения в
управленческом, бухгалтерском и налоговом учёте не используются как фильтр.

Для определения внутреннего перемещения сервис использует уже построенное соответствие
складов из выгрузки. Дополнительный поиск свойств складов не выполняется. Передачи между
физическими складами с одним `warehouse_mapping_id` исключаются, между разными
логическими складами проверяются. При пустых полях отправителя и получателя сервис
распознаёт внутреннюю передачу по двум физическим складам одного документа и нулевому
суммарному движению каждого товара внутри логической группы.

## Типовые ошибки

### `Unexpected token '<', "<!doctype "... is not valid JSON`

Браузер получил HTML вместо JSON или Excel-файла. Проверьте, что форма открыта через `http://127.0.0.1:8000/`, а не напрямую как `file://.../index.html`.

### `Не задан обязательный параметр конфигурации ONEC_TRADE_URL`

Не создан `.env` или не заполнен URL базы управления торговлей.

### `ONEC_TAX_BASES_JSON должен быть валидным JSON`

В переменной `ONEC_TAX_BASES_JSON` нарушен JSON-синтаксис. Проверьте кавычки, запятые и квадратные скобки массива.

### `Не удалось получить данные из базы ...`

1С-эндпоинт недоступен, вернул ошибку, не принимает параметры `start_date`/`end_date` или указаны неверные учетные данные.

### `У пользователя 1С нет права на HTTP-метод GET`

URL и метод запроса определены, но роль пользователя в указанной базе 1С не разрешает GET для
HTTP-ресурса. Проверьте права пользователя и публикацию HTTP-сервиса; переключение на POST не поможет,
если endpoint отвечает `405 Method Not Allowed`.

### `422 Unprocessable Entity`

Тело запроса к `/reconcile` не соответствует модели. Проверьте формат дат `YYYY-MM-DD`; `end_date` должен быть больше или равен `start_date`.
