# Проверка интеграции 1С

Цель: подтвердить корректное получение трёх выгрузок, сохранность данных при нормализации,
достоверность сверки и Excel. Исправлять воспроизводимые дефекты интеграции с регрессионными
тестами. Использование эндпоинтов складов и фильтра не должно нарушать выгрузку без фильтра.

## Подтверждённый контракт на 07.09.2026

Проверены URL с префиксом `https://internal.internal.example.invalid/obmendb/hs/main/`:

| База | Путь | Рабочий запрос | Строк за контрольный период |
| --- | --- | --- | ---: |
| УТ | `data1C/stocksturnover` | GET с JSON-телом | 28 406 |
| БУХ2019 | `dataBUH2019/stocksondate` | GET с JSON-телом | 12 910 |
| БУХ2026 | `dataBUH2026/stocksondate` | GET с JSON-телом | 13 984 |

Тело запроса без склада:

```json
{"periodBegin":"20260301","periodEnd":"20260401"}
```

Ответ: объект `{"code":200,"data":[...]}`. В данных есть строки 01.04.2026 23:59:59:
заданный период включает 1 апреля и не равен только марту. Авторизация Basic с UTF-8
проверена текущими учётными данными проекта на всех трёх URL.

GET с query-параметрами возвращает сентябрьские данные вместо запрошенного марта.
POST возвращает пустое тело HTTP 200 для УТ и HTTP 405 для обеих БУХ.
Заголовок Content-Type у рабочих ответов отсутствует. Период 19000101–19000101
возвращает пустой `data`; некорректная дата `invalid` возвращает HTTP 500 с JSON.

## Выполненные проверки и исправления

1. Сохранены исходные тела ответов, параметры, статусы, длительность и SHA-256.
   Файлы находятся в игнорируемом Git каталоге `outputs/onec/`; заголовки авторизации не сохраняются.
2. Прямые ответы сравнены с повторными живыми запросами через `OneCClient`.
   Все строки совпадают как мультимножества: порядок может меняться, число повторов учитывается.
3. Независимый разбор исходных чисел подтвердил сохранение всех шести показателей
   каждой строки. `None` и `[]` не отправляют фильтр складов.
4. Добавлен `request_payload=json` для GET. Режим `auto` сохраняет прежнее поведение
   GET/query и POST/JSON для других сервисов.
5. Добавлены бухгалтерские алиасы `СуммаНачальныйОстаток`, `СуммаОборот`,
   `СуммаКонечныйОстаток`; сохраняются коды номенклатуры, артикулы, склады и организации.
6. Убрано округление при нормализации: в реальной УТ есть количества с тремя знаками.
   Денежный допуск отделён от количественного; количества по умолчанию сравниваются точно.
   Неконечные числа, ошибки в поле `code`, пустой/некорректный JSON не дают успешную сверку.
7. Ключ учитывает код номенклатуры и склад, с резервным использованием названия при отсутствии кода.
   До исправления 5 416 групп УТ, 3 306 групп БУХ2019 и 3 307 групп БУХ2026 смешивали склады.
   После исправления ключи всех строк контрольной выгрузки уникальны.
   Повторяющиеся ключи УТ считаются неоднозначными; их остатки не суммируются автоматически.
8. В Excel добавлены идентификаторы и организация. Проверены значения всех шести числовых
   столбцов и идентификаторы всех 81 915 строк диагностического отчёта.
   Это число результатов буквального сопоставления, а не подтверждённых ошибок учёта.
   На компактном образце проверены закреплённая шапка, автофильтр, ширины колонок,
   читаемость заголовков и первых строк.
9. Неподдерживаемый фильтр складов отклоняется до загрузки данных любой базы, HTTP 422.
   Несогласованный JSON-мультивыбор отклоняется вместо потери всех складов, кроме последнего.
   Справочник с одинаковыми именами и разными идентификаторами отклоняется вместо объединения.
10. Локальная `.env` переведена на проверенные URL и GET/JSON. Бухгалтерские базы используют
    явные `username_env`/`REDACTED_env` со ссылками на существующие переменные; секреты не дублируются.
    Одинаковые имена бухгалтерских баз запрещены: иначе одна выгрузка перезаписывает другую.

## Контроль остатков

Нельзя суммировать начальные/конечные остатки всех строк движений за период.
Для каждой пары номенклатура/склад выделены начало и конец последовательности остатков.
При нескольких документах в одну секунду конечное значение определяется по связности
переходов начальный→конечный остаток, независимо от порядка строк и проверяемого итога.
Неоднозначные цепочки не подгоняются под контрольную сумму.

| База | Начальное количество | Оборот количества | Конечное количество | Конечная сумма |
| --- | ---: | ---: | ---: | ---: |
| УТ | 5 938 348,877 | 196 804,780 | 6 135 153,657 | 2 244 817 984,34 |
| БУХ2019 | 5 351 389 | 60 753 | 5 412 142 | 1 687 193 560,41 |
| БУХ2026 | 5 351 392 | 60 660 | 5 412 052 | 1 931 708 731,81 |

Во всех трёх базах контроль начала + оборота = конца проходит по количеству и сумме
для всех групп; неоднозначных граничных цепочек нет.
Числа характеризуют целиком каждую выгрузку, их область учёта между базами ещё не согласована.

У 40 позиций БУХ2026 на складе `БД-000003` нет отдельного пустого документа на конец:
вместо него есть документы 01.04.2026 23:59:59. Проверка только пустых документов
ошибочно занижала итог на 894 920 и 391 421 328,61. Это исправленная ошибка метода анализа,
а не доказанный дефект 1С. В `audit.json` сохранены оба способа для воспроизводимости;
правильный контроль отражён в `transition_based_control`.

Без таблицы соответствия можно достоверно сравнить пары, где одновременно совпадают
`НоменклатураКод` и `СкладКод`. Для этих пар начальные остатки, обороты и конечные
остатки по количеству совпали полностью:

| Сравнение | Совпавшие пары товар/склад | Все количества совпали | Все суммы совпали | Конечная сумма совпала |
| --- | ---: | ---: | ---: | ---: |
| УТ — БУХ2019 | 383 | 383 | 91 | 97 |
| УТ — БУХ2026 | 384 | 384 | 60 | 67 |

Это подтверждает количественную согласованность общей области данных. Различия стоимости
требуют проверки правил оценки запасов в УТ и БУХ. Остальные склады нельзя автоматически
считать отсутствующими: их коды и названия различаются, и нужна утверждённая таблица соответствия.

## Оставшиеся условия приёмки

| Этап плана | Текущее состояние | Что ещё требуется |
| --- | --- | --- |
| 1. Контракт | HTTP и числовые поля подтверждены | Область учёта, соответствие складов и документов |
| 2. Прямые запросы | Выполнены | Согласовать требуемые статусы ошибок с 1С |
| 3. Клиент и нормализация | Проверены на всех 55 300 строках | Повторять после изменения контракта |
| 4. Сверка и штатные отчёты | Есть диагностическая сверка и контроль баланса | Штатные отчёты 1С и утверждённые правила сопоставления |
| 5. Доработки | Исправления и регрессионные тесты выполнены | Исправлять новые подтверждённые дефекты |
| 6. Подготовка складов | Справочники, явное соответствие, выбор по ID и fan-out нескольких ID реализованы | Добавлять утверждённые соответствия складов |
| 7. Живые склады | Три endpoint и фильтрация проверены | Повторять контроль после изменений 1С |
| 8. Полный маршрут и Excel | ASGI-тесты, живой HTTP 200, XML/значения и отображение проверены | Бизнес-приёмка |

УТ не возвращает организацию, обе БУХ содержат одну организацию. Склады между базами
часто имеют разные коды и названия, документы также могут иметь разные представления.
Без таблиц соответствия метки «отсутствует»/«лишняя» остаются диагностическими.
Бухгалтерские базы не объединяются: пересечение их данных и назначение ещё не подтверждены.

Справочники являются источником актуальных имён и кодов, но не источником межбазовой связи:
соответствия задаются явно в `ONEC_WAREHOUSE_MAPPINGS_JSON`. Для каждого нового соответствия
нужно повторить прямую и клиентскую выгрузку, проверку подмножества, баланса, `/reconcile` и Excel.

Одному логическому складу можно назначить несколько кодов одной базы. Это необходимо,
если `Основной склад` БУХ объединяет несколько секций или внутренних складов УТ.
Граничные строки остатков таких физических складов суммируются перед сравнением.

Документы больше не сравниваются по полному представлению. Основное правило использует
совместимую группу типа, номер и дату/время. Реализации с разными номерами могут быть
сопоставлены по уникальному сочетанию даты/времени, товарных строк и количества движения.
Если сочетание не уникально, результат помечается для ручной проверки.

## Складские endpoint и фильтрация — 08.09.2026

Подтверждён единый контракт справочников УТ, БУХ2019 и БУХ2026: `GET` без параметров,
ответ `{ "code": 200, "data": [...] }`, поля записи `Склад`, `Код`, `Группа`.
После схлопывания полностью идентичных повторов получено 268, 17 и 16 уникальных кодов соответственно.
Конфликтующие записи с одинаковым кодом приложение отклоняет.

Фильтр выгрузки передаётся одиночным полем `warehouse` в JSON-теле GET. Проверено
соответствие `upr000234_bd000001`: УТ `УПР000234`, БУХ2019 и БУХ2026 `БД-000001`.

| База | Полная выгрузка | Фильтрованная | Группы баланса | Ошибки баланса |
| --- | ---: | ---: | ---: | ---: |
| УТ | 28 406 | 3 255 | 250 | 0 |
| БУХ2019 | 12 910 | 4 154 | 322 | 0 |
| БУХ2026 | 13 984 | 4 057 | 314 | 0 |

Для всех трёх баз одновременно подтверждено:

- в фильтрованном ответе присутствует только запрошенный `СкладКод`;
- результат `OneCClient` равен прямой выгрузке как мультимножество нормализованных строк;
- фильтрованная выгрузка равна подмножеству полной выгрузки по `СкладКод`;
- начальный остаток + оборот = конечный остаток для количества и суммы;
- `/reconcile` вернул корректный XLSX размером 1 664 017 байт.

Число 13 961 относилось к прежнему буквальному сравнению полных представлений документов
и всех промежуточных остатков. После внедрения сопоставления по типу, номеру и дате оно
не является контрольным показателем.

Воспроизведение проверки:

```powershell
.venv\Scripts\python.exe -m scripts.probe_onec `
  --warehouse-mapping upr000234_bd000001 `
  --begin 20260301 --end 20260401 --timeout 120
```

Артефакты контрольного запуска: `outputs/onec/20260908T074013602730Z`.

## Автоматическое сопоставление складов — 10.09.2026

В справочнике УТ появилось поле `СкладБухгалтерия`. Приложение группирует все склады УТ
с одинаковым заполненным значением этого поля и связывает группу с одноимённым складом
каждой бухгалтерской базы. Сравнение названий учитывает Unicode, регистр и повторяющиеся
пробелы, но не использует нечёткие эвристики.

Живая проверка справочников подтвердила 11 полных логических соответствий и 108 связанных
складов УТ. У 148 складов связь пустая; ещё 12 складов содержат 5 значений, отсутствующих
в обеих БУХ. Они отражаются в `mapping_diagnostics` и не блокируют сверку полных соответствий.
Группа «Основной склад» объединяет 78 складов УТ, включая `УПР000234`, и сопоставляется
с `БД-000001` в БУХ2019 и БУХ2026.

Для одного физического кода сохраняется серверная фильтрация. Если выбранная область
содержит несколько кодов одной базы, приложение делает одну полную выгрузку этой базы,
локально оставляет выбранные коды и назначает строкам общий `warehouse_mapping_id`.
Ручные записи `ONEC_WAREHOUSE_MAPPINGS_JSON` используются только как подтверждённые
исключения; совместимая запись расширяет автоматическую группу и сохраняет прежний ID.

## Сверка документов без GUID — 08.09.2026

GUID в текущих выгрузках отсутствует и для сверки не требуется. Основное правило использует
совместимую группу типа документа, номер и точную дату/время. Для реализаций с разными
номерами разрешено только уникальное совпадение по дате/времени, товарам и количеству.
Повторяющиеся строки одного товара внутри документа агрегируются перед сравнением.

Контрольная выгрузка повторно обработана для соответствия складов
`УПР000234` → `БД-000001`:
